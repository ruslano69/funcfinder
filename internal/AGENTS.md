# internal/

## Purpose

Core parsing engine. Implements function/struct discovery, body extraction, call-graph analysis, dependency resolution, shard splitting, output formatting, and incremental update logic for all 15+ supported languages.

## Ownership

- All language-specific parsing logic lives here.
- `cmd/` packages are consumers only; they must not bypass the public API of this package.
- Test files (`*_test.go`) are co-located with the code they test.

## Local Contracts

- Public API surface: `FindFunctions`, `FindStructs`, `ProcessDirectory`, `BuildCallGraph`, `WriteSplitOutput`, `WriteSplitOutputIncremental`, `ForEachParallel`, `FindFunctionsInFile`, `LanguageConfig.FuncSubmatch`, `ReadCodeObject`, `ReplaceCodeObject`, `PlanCodeEdits`.
- Structural edit: `ReplaceFunction` replaces one function and `InsertAfterFunction` adds new functions after one and `RemoveFunction` deletes one (`edit.go`, `edit_remove.go`), for any language. Limits: `docs/EDIT.md`. It takes the span from the language's finder, trims trailing blank lines, and refuses unless the old text matches (when given), the replacement's brackets balance (brace languages), and the finder finds the same functions and types in the same order in the new file. Go also checks its span and the top-level declarations against `go/ast` (`edit_go.go`). Line endings are kept; mixed endings are refused.
- Shared-line Go functions use exact AST byte spans in `edit_go_shared.go`; the Go lexer locates explicit separator semicolons without interpreting literal/comment contents. Replacement preserves receiver identity; all operations reparse and check declaration order. Neighboring bytes are retained, `--old` accepts the fragment or full covering lines, and ambiguous same-line names remain refused. Other languages retain whole-line restrictions.
- `shared_line_functions.go` recovers same-line declarations for Go, C, C++, D, Rust, Swift, Kotlin, PHP and Ruby by exposing cleaned structural boundaries to existing language parsers. Delimiters inside literals/comments and parenthesized/bracketed expressions are excluded. Results and extracted text map back to physical source lines, including nonzero offsets and D rune-to-byte translation. Complete canonical Go files use AST bounds on this recovery path; fragments/custom patterns retain configured recognition. Native C#/Java/JS and existing TS/Scala paths are unchanged. Finding shared declarations does not authorize whole-line edits in other languages. `shared_line_functions_test.go` covers names, selection, scopes, literal guards and source bounds.
- Single-file function map output (`formatter.go`) marks positive equal start/end bounds with `[one-line]`; its JSON includes `single_line: true` only for these entries. This means a one-line span, not proof of shared code. Extraction headers remain unchanged for edit guards.
- Type edit targets use `edit_go_types_ast.go`, not struct-finder spans: top-level Go `TypeSpec` nodes support generics, aliases, grouped members and shared lines. `--line` and strict `--old` select/guard the actual declaration; grouped edits preserve wrappers, convert complete input type declarations into specs and refuse comments outside those specs. Insertion rejects non-types and duplicate top-level names; non-Go type edits fail closed. Whole-file parsing and declaration-order checks do not establish type/behavioral compatibility. `edit_go_types_ast_test.go` verifies byte preservation, guards and grammar cases.
- `code_object.go` owns the Go backend of `funcfinder.code/v1`: exact Go function/type source, opaque coordinate identities, whole-file SHA-256 revisions and pure validated replacement. Group members expose complete type declarations. Ambiguity returns editable candidates. Only `source` is mutable; stale/altered envelopes and changes to neighboring declarations are refused. Core checks cover grammar/identity, not type or behavioral contracts. `code_object_test.go` covers shared lines, methods, groups, stale guards and EOL preservation.
- `code_edits.go` plans Go JSON replace/insert_after/remove operations against one original file snapshot. `funcfinder.edits/v1` batches validate every envelope, reject stale/mixed-file/overlapping requests and check the complete final declaration sequence before any write. Group insertion accepts only types; top-level insertion accepts functions/types. Results follow request order with final revisions and refreshed inserted/replaced objects; removals have empty object arrays. Caller owns the single staged write. `code_edits_test.go` covers mixed transactions, no-mutation failures, duplicates, comments, EOF and EOL preservation.
- Rust JSON objects use byte tokens and scoped item discovery in `rust_objects.go`; `rust_code_edits.go` dispatches to the common token transaction planner in `token_code_edits.go`. Include outer attributes and require them unchanged on replacement; leave preceding docs outside. Respect module/impl/trait/extern scope, opaque macro token trees/function bodies, raw/byte/C literals, lifetime-vs-char quotes and nested comments. Struct/enum/union/trait/type-alias objects and methods/bodyless trait/extern functions share the revision/identity/overlap protocol. `rust_tokens_and_declaration_identity` is structural validation, not full Rust grammar/type checking. No macro expansion/cfg evaluation/local function-item discovery; unsupported shapes fail closed. `rust_code_objects_test.go` pins source truth, scoped ambiguity, attributes, container overlap and EOL preservation; compiler/itoa checks are described in `docs/EDIT.md`.
- C# JSON objects use `csharp_objects.go` and the shared token transaction planner. Byte tokens handle comments and normal/verbatim/raw/interpolated literals; preserve attributes, explicit interface qualification and constructor category. Methods/constructors/destructors/operators/conversions/bodyless declarations and nominal types retain lexical namespace/type ownership, generic arity and overload candidates. Fields/properties/events/accessors/delegates/local functions/top-level statements are not objects. Conditional directives and assembly/module attributes refuse the file; harmless directives are noneditable catalogue entries. `csharp_tokens_and_declaration_identity` is structural, not full grammar/type/overload resolution. `csharp_code_objects_test.go` covers spans, guards and transactions; Roslyn/runtime/sample evidence and limits live in `docs/EDIT.md`. Go/Rust contracts and navigation remain unchanged.
- D JSON objects use `d_objects.go` and the shared token transaction planner. Byte tokens pair brackets after nested comments and D literal forms, including q-token/delimited strings. Existing regex-free `dHeaderSubmatch` recognizes token-reconstructed headers; contract/template/body spans stay byte-based. Functions/methods/constructors/property functions and nominal types/modern aliases retain lexical template/attribute ownership; prefixes/UDAs and post-parameter attributes are preserved. Function/unittest bodies are opaque. Conditional/mixin declaration scopes and line directives refuse the file. `d_tokens_and_declaration_identity` is structural, not grammar/type/template checking. `d_code_objects_test.go` and the LDC/tree-sitter examples in `docs/EDIT.md` pin the scope, spans and transaction checks. Navigation and other backends retain their contracts.
- JS/TS JSON objects use the byte lexer and scoped catalogue in `script_objects.go`, with `scriptObjectPatch` preserving declaration-list/object-member commas in the common token transaction planner. Named functions, direct function-valued bindings/members and named class/interface/type declarations are objects; namespaces, ambient global scopes, control blocks and directly assigned objects retain lexical ownership. Variable objects expose synthetic complete const/let/var declarations at physical binding coordinates. Function bodies/call arguments are opaque; computed names, anonymous declarations, class expressions and wrapped function values are outside the selectable profile. Decorators/prefixes and shared-line neighbors are preserved. `javascript_typescript_tokens_and_declaration_identity` is structural, not full grammar/type validation. `script_code_objects_test.go` pins spans/transactions/guards; opt-in `TestScriptCodeObjectsCorpus` consumes `benchmarks/script_objects_oracle.cjs` output through `FUNC_SCRIPT_ORACLE`, optionally writing `FUNC_SCRIPT_REPORT`. Report source-truth differences, excluded files and mixed-EOL preview refusals separately. Navigation tokenizers remain unchanged; measured scope and limits live in `docs/EDIT.md`.
- Kotlin JSON objects use `kotlin_objects.go` and the common token transaction planner. Named top-level/member/extension functions and named class/interface/object/companion/alias types use exact code-token byte spans. Preserve annotation/modifier/context/receiver prefixes; overloads use lexical signature keys. Nested comments, quoted/raw/interpolated strings and backtick names are tokenized before bracket pairing. LF-normalize literal token keys for payload comparison while retaining original CRLF source bytes. Named val/var properties (including delegates) and explicit get/set are `property`/`accessor` objects. Properties own accessor spans; parent/child edits overlap. Accessor insertion is restricted to get/set, val refuses setters, and duplicate accessors are refused. Preserve val/var/receiver and accessor attributes/visibility. Initializer/function/accessor bodies and enum entries are opaque; constructor parameters, destructuring, secondary constructors and local/anonymous declarations are not separate objects. Unnamed companions retain nested named members as noneditable scopes. `kotlin_tokens_and_declaration_identity` is structural, not full grammar/type/compiler validation. `kotlin_code_objects_test.go` pins spans/transactions/guards; opt-in `TestKotlinCodeObjectsCorpus` consumes `benchmarks/kotlin_objects_eval.py` output through `FUNC_KOTLIN_ORACLE` and optional `FUNC_KOTLIN_REPORT`. Keep source-truth differences, PSI/parser exclusions and edit-guard refusals explicit. Navigation and D finders are unchanged; scope/evidence lives in `docs/EDIT.md`.
- Language dispatch is handled by `finder_factory.go` (functions) and `struct_finder_factory.go` (structs); new languages must register here.
- `languages.json` is the canonical list of supported file extensions → language identifiers.
- Go `exclude_words` lists all reserved keywords so `funcstats` does not count parenthesized control/return expressions as calls. Predeclared functions and type conversions remain eligible; do not exclude them as keywords. `cmd/funcstats` pins this with a syntax-checked Go regression.
- Shard output goes to `.codemap/` by default; manifest is `.codemap/manifest.json`.
- Incremental mode (`--inc`) uses xxh3 checksums (`checksum_xxh3.go`) with stdlib fallback (`checksum_stdlib.go`).

## Work Guidance

- Adding a new language: implement the `Finder` interface, register in `finder_factory.go` and `struct_finder_factory.go`, add the extension in `languages.json`, add test fixtures in `test_examples/`.
- C++ is migrating incrementally: `cpp_members.go` uses shared brace tokens to recover builtin conversion operators and members with ref qualifiers/conditional `noexcept`, and adds nested class scopes before the legacy function scan. Choose the nearest enclosing C++ class. Recovery scans all function bounds before applying name selection, excludes existing bodies and continued directives, and preserves original extraction and offsets. Alias/dependent conversion types still need semantic resolution; this is not a complete C++ token parser.
- `cppExpressionHeaders` rejects legacy C++ header matches only with token evidence of expressions: member access in non-default arguments, reference/address expressions, stream insertion or qualified calls without return types. Preserve ellipses, default arguments, repeated names in trailing returns/delegating initializers, template names and split return types. This is conservative false-positive recovery, not semantic C++ declaration resolution.
- Ruby block discovery strips a simple singleton receiver only for configured method-name matching; `def logger.warn`, `def @agent.receive` and qualified constant receivers report the method name. Keep source extraction and selection/line offsets intact. This does not implement arbitrary Ruby receiver expressions or full nested Ruby parsing.
- C function recognition in `languages.json` accepts parenthesized names in definitions/prototypes. A pointer declarator `(*name)` must not turn its return type into a function name; preserve original extraction and offsets. `c_parenthesized_test.go` covers these boundaries and selected-function mode.
- `enhanced_sanitizer.go` strips string literals and comments before parsing to prevent false positives; touch it carefully and run its bench test after changes.
- `python_finder.go` and `python_lines_processor.go` handle Python's indent-based scope; keep them in sync.
- Both Python paths share logical-statement boundaries: continuation lines and string contents do not dedent a scope, suite colons are read outside brackets, and inline suites end with their logical statement. Finder class ranges use the same rules; extraction retains original source and trailing trivia.
- PHP uses the nested finder so methods of classes inside functions are visible. `php_heredoc.go` masks heredoc/nowdoc text before function/class discovery, preserves trailing code after closing labels and restores original source for function extraction, including offset scans.
- D preparation in `d_lines.go` masks nested comments/literals, contracts and declaration prefixes, joins multiline return-type headers with original end coordinates, and rejects statement/type headers. D uses nested discovery with the nearest class scope; constructor-delegation calls must be filtered even in selected-function mode, while local constructors/postblits remain visible. Extraction retains original source. Reserved words and types are excluded as names. `prepareDLines` runs the function pattern only through `dFuncHeader`, which applies the `func_requires` gate (`(`) first, and runs `dAttributeLine` only on non-blank lines: blanked comments make long space-only lines, where the patterns backtracked for most of a D run. The header-join pre-check runs its cheap tests before `dFuncHeader`; a statement line (first character replaced with `?`) skips `dFuncHeader`, which `TestDStatementLinesNeverMatchFuncHeader` guards; `findDClasses` runs the class pattern only where `MayStartType` holds. `prepareDLinesHinted` also returns each prepared line's function-pattern result (`dHintMatch`/`dHintNoMatch`), recorded only when the checked text is the line's final text; the finder keeps it in `Finder.dFuncHint` for the scan and skips the pattern on `dHintNoMatch` lines (`TestDFuncHintMatchesPattern`). The third pass converts each line to runes once and back only after a change. `dAttributeLineMatch` gates `dAttributeLine` on the first character (`TestDAttributeGateNeverHidesAMatch`). `dLineLexer.cleanLine` returns a line as it is in the normal state when it is plain ASCII code (`dPlainCode`), and `normalizeDPrefix` when its first word is ordinary and the line is valid UTF-8 (`dPlainPrefix`); the full paths are `cleanLineSlow` and `normalizeDPrefixSlow`, and `TestDLexerFastPathsMatchSlow` compares them, lexer state included. A change to either full path must keep its fast check in step. The D `func_pattern` is not run: `dHeaderSubmatch` (`d_header.go`) walks the same structure and returns exactly what `FindStringSubmatch` returns (match and groups, chosen leftmost-first). It is used only while `languages.json` holds `dFuncPatternSource` byte for byte (`dUsesHeaderScanner`); a change to the D `func_pattern` must change the constant and the scanner together, and `TestDHeaderScannerPatternIsCurrent` / `TestDHeaderScannerMatchesPattern` (fixture lines, header joins, random and structured lines) must pass. `LanguageConfig.FuncSubmatch` is the entry point for callers outside the finder (`callgraph`, `funcstats` signature lines).
- Scala preparation and endpoint checks in `scala_lines.go` handle braceless expressions, bodyless declarations, multiline signatures/literals, symbol-vs-char quotes and inline members. Function recognition stays configured in `languages.json`; shared nested-parser and sanitizer implementations are unchanged.
- C# (`csharp_finder.go`) tokenizes shared `LineFacts` and matches declarations by their return type, parameter list and enclosing type. It retains constructors/destructors, operators, explicit interface members, generic and local functions, and bodyless declarations. Properties/indexers/events are scope boundaries; object initializers and patterns retain their expression context. Expressions end at their outer semicolon, including lambdas/initializers; a conditional expression's source range includes its last branch, without evaluating preprocessor symbols.
- Java (`java_finder.go`) uses a linear token walk with an explicit brace stack. Only named/local/anonymous type bodies accept members; ordinary function/control blocks do not. Keep annotation arguments, generic/annotated return types, throws clauses, compact record constructors and bodyless annotation defaults distinct from calls or method bodies. Return original source for extraction, including leading declaration annotations. Type starts use the keyword line to deduplicate the directory structural pass. `java_finder_test.go` pins contexts, dollar names, Java-specific reserved words, enum constant bodies, source offsets/selection and nested caller attribution.
- `braceTokens` in `csharp_finder.go` shares bracket pairing and line coordinates. `csTokens` keeps C# lexical rules; Java enables dollar identifiers explicitly. A Java recognition change must not add C# reserved words (`delegate` is a Java method name) or change C# tokenization.
- C#, Java and JavaScript bounds carry non-serialized `SignatureLine`/`SignatureName` metadata. `callgraph` and `funcstats` exclude that declaration token once, retaining genuine recursion, including on the same line. These languages attribute calls to the innermost named function. A JS arrow/anonymous variable value has no name/parenthesis declaration token and must not lose a real recursive call to a regex fallback. Other languages retain regex signature detection. Original extraction and nonzero line offsets must stay correct.
- JavaScript (`javascript_finder.go`) discovers functions independently of the TypeScript line scanner. Build tokens from shared `LineFacts`; recover masked literals only as opaque names/endpoints and retain bracket pairs. Named expressions use their internal name; anonymous direct identifier-variable function/arrow values use the binding name. Do not name an anonymous IIFE by the variable receiving its return value. Uninitialized/continued declarators and newlines before function bodies stay part of their declaration. An explicit delimiter stack limits method discovery to class/object members, excluding callback arguments. Preserve duplicate names, original extraction and offsets. `javascript_finder_test.go` covers minified neighbors, dollar/private/quoted/numeric/keyword methods, literal guards, binding context, nested callers and `.cjs` detection.
- JS/TS templates use `javascript_template.go`'s incremental frame stack in both line cleaning and whole-file token recovery. Escaped backticks, nested templates, comments and regex literals inside interpolations must not close the outer template. Every template opens with an empty frame stack, whatever its closing delimiter: frames of a template an earlier text left open must not carry over (`TestCleanLinesFactsIgnoresEarlierFiles`). JS/TS block comments close at the first `*/`; other languages retain their existing comment handling. A JS regex cannot have unknown identifier flags. `js_ts_misses_test.go` covers these lexical boundaries.
- JS supports `.js`, `.jsx`, `.mjs` and `.cjs`. `{JS_IDENT}` in `languages.json` expands to the JS identifier rule shared with its lazily compiled callgraph regex, including dollar/private names; other languages retain `{IDENT}`. JS class/call patterns must agree with those names. The frozen recursive experiments do not participate in this production path.
- `csharp_recursive_test.go` is an experimental recursive brace-scope traversal, sharing production tokenization/signature/end rules. It is test-only; `csharp_compare_test.go` checks complete-result parity (including extraction, offsets and signature metadata) and benchmarks both on tracked files from `CSHARP_COMPARE_ROOTS`. `benchmarks/csharp_traversal_compare.py` uses a Go overlay to test/build the prototype as a CLI without changing the default finder.
- The shared recursive pilot targets C#, Java and D; Python and Ruby are excluded, and Scala's indentation syntax is outside this brace-scope pilot. `brace_recursive_test.go` consumes adapter events and owns nesting, context and extraction without language keywords. `brace_adapters_test.go` owns language preparation/recognition and source coordinates; it reuses C# token/endpoint utilities and D's prepared contracts/literals. `brace_pilot_test.go` covers Java annotations/compact constructors and D contracts, access sections, conditional declarations, case labels and constructor-delegation calls. Keep it test-only until promotion is separately validated; `benchmarks/brace_pilot_build.py` builds/tests an overlay against the same CLI and API consumers.
- `d_traversal_bench_test.go` compares the full production D path and shared recursive pilot in one test binary on preloaded tracked `.d` files from `D_COMPARE_ROOTS`. `D_COMPARE_REVERSE=1` reverses variant order. Include preparation and class discovery in both; keep disk I/O outside the timer. This compares complete implementations, not recursion in isolation. `benchmarks/d_traversal_compare.py` records repeated parser and CLI timings against verified pilot binaries.
- `brace_parallel_test.go` is an optional test-only scope scheduler for the shared pilot. Preparation/tokenization stay serial per file. One process-wide budget permits at most `FUNCFINDER_SCOPE_WORKERS - 1` additional tasks (default CPU count minus one), with `FUNCFINDER_SCOPE_MIN_TOKENS=2048`; small scopes or unavailable permits run inline. Tasks own result slices and join in source order. These environment variables are overlay experiment controls, not production CLI settings. `brace_parallel_check_test.go` verifies ordered parity, extraction/offsets/selection, shared-file scheduling and permit return; `BRACE_PARALLEL_PROJECTS` supplies JSON language/root pairs for complete-corpus parity. Preserve the serial implementation and its measured hashes when changing this experiment.
- C++ (`cpp` in `languages.json`) runs the simple scan with its header patterns; the other languages have none of them. `func_pattern` takes nested parentheses in parameters, a body on the header line, `operator` names, qualified constructors and a template prefix. `header_open_pattern` starts a signature that continues on later lines (any scope); `constructor_pattern` matches a constructor only inside a class and only when its name is that class's name (or `~` it); `declaration_pattern` matches a bodyless declaration ending in `;`, whose parameters are typed (a literal or a lone name is a direct initialization such as `Widget w(42);`); inside a class body `member_declaration_pattern` also takes a lone name. A line that starts with a `statement_words` entry is a statement, not a header; `conversion_operator_pattern` drops conversion operators, which the finder does not name. `initializer_lists` makes a constructor's `member{...}` a braced initialization rather than the body: `sigScanner.bodyAt` tells the brace counter where the body starts. Class bodies end by net brace depth, so a one-line class (`struct A : B {};`) does not hold the next class open. `class_pattern` skips a `template <...>` prefix and an export macro (`class FMT_API name`). Measured by `benchmarks/cpp_tree_eval.py`.
- TypeScript (`ts`, nested scan): `class_pattern` takes `export`/`default`/`abstract` modifiers and `interface`; a class header may span lines, so a class closes only after its body has opened and closed (`classOpened`), and a header with no body that is complete closes on its own line (`classHeaderContinues`). `declaration_pattern` (ts) lists bodyless signatures: overloads, interface and class signatures with a return type, and `abstract` methods; it is tried only at the top of a scope. A `const|let|var name = (` header is a value unless an arrow or a return type follows the parenthesis that closes on its line (`assignedParen`). `open_type_header_pattern` opens a typed header whose type argument runs over lines (`const X: React.FC<{`, `async list(): Promise<`), and `typedHeaderIsFunction` decides it. A `{` after `<` is a type literal (`sigScanner.typeBraces`; `braceDeltaSkippingTypeLiterals` in the nested scan): its braces and any `;` inside are not the body or the end of the signature. A body that opens and closes on its header line ends there (`bodyOnLine`); what follows its closing brace belongs to the caller. A later declarator of a `const|let|var` list on the same line (`const id = f(), notification = (x) => ...`) is read after its `,` with `declarator_pattern`, when its statement starts at the line start or after a `;` or `{` outside brackets (`listDeclarationBefore`); the list's keyword applies to it.
- TypeScript `func_pattern` is not run: `tsHeaderSubmatch` (`ts_header.go`) returns exactly its `FindStringSubmatch` (match and all seven groups; the nested scan reads group 4), in leftmost-first order, including the lazy type annotations. It is used only while `languages.json` holds `tsFuncPatternSource` byte for byte (`tsUsesHeaderScanner`), by the nested scan, the inline-header search (`inlineStart.tsScan`) and `LanguageConfig.FuncSubmatch`; a change to the TS `func_pattern` must change the constant and the scanner together (`TestTSHeaderScannerPatternIsCurrent`, `TestTSHeaderScannerMatchesPattern`). `quoted_method_pattern` (TS, JS) runs only where `MayQuoteMethod` holds: a quote after leading whitespace (`TestMayQuoteMethodNeverHidesAMatch`).
- `typescript_candidates.go` supplements that canonical TS path when an unresolved header-shaped line remains. Balanced tokens recover nested/multiline generics, split/curried arrows, dollar-named declarations, quoted and keyword methods and multiline object methods. Keep class/object member scopes distinct from executable case blocks; asserted/invoked function values retain the existing named-function profile exclusions. Merge duplicates one-to-one by name/start without changing existing bounds; replace the spurious `async` entry for an async quoted method. Custom function patterns bypass this recovery. The whole-file token pass is costly, so `tsCandidateFile` lets a file through only for a shape the pass can read: a `(` line whose raw text starts (after modifiers and block comments) with a quoted name (`tsQuotedNameFirst`); a split `const x =` value whose parenthesis is followed by `=>` or `:` (`tsParenValue`); a generic list followed by a parameter list and `:`/`{` (`tsCandidateGeneric`). A parenthesis or type list that continues over lines is read through `tsJoinedText` (the next `tsJoinLines` lines); one that does not close there still passes. A new recovery shape needs its gate rule; `TestTSRecoveryGateShapes` pins the shapes, and a gate change must keep the output of the unnarrowed gate on real trees. Preserve selection, class scopes, source extraction and nonzero offsets (`TestTSMissingHeaderShapes`, `TestTSRecoveredSelectionOffsetsAndExtraction`).
- TypeScript `declaration_pattern` and `declarator_pattern` are not run either: `tsDeclarationSubmatch` and `tsDeclaratorSubmatch` (`ts_declaration.go`) return exactly their `FindStringSubmatch` (the whole line and the name of the signature or `abstract` member; the match up to the value's `<` or `(` and the name), including which of the two declaration alternatives wins and the lazy type annotation, which the declarator shares with the `const|let|var` header (`tsAssignedValue`). They are used only while `languages.json` holds `tsDeclarationPatternSource` and `tsDeclaratorPatternSource` byte for byte (`tsUsesDeclarationScanner`, `tsUsesDeclaratorScanner`), by the nested scan (declaration, after the `MayDeclare` gate) and the inline-header search (declarator, `inlineStart.declScan`); a change to either pattern must change its constant and scanner together (`TestTSDeclarationScannerPatternsAreCurrent`, `TestTSDeclarationScannersMatchPatterns`: fixture lines, every suffix of a cleaned line, random and structured lines).
- Call graph logic (`callgraph.go`) operates on the output of the finder layer, not on raw source.
- Overlapping Go function line ranges use `callgraph_go_shared.go`: parse the file and inspect only selected declarations' AST bodies to assign calls to their exact owner and exclude neighboring signatures/global initializers. Closures belong to the enclosing named function; bare-name filtering, import aliases, edge deduplication and physical call lines are retained. This remains a name-based graph without type resolution. Files without overlapping ranges keep the existing scan; unparseable fragments retain its fallback. `TestBuildFileCallGraph_GoSharedLineOwnership` covers file and directory modes.
- `BuildDirCallGraph` reuses the directory job's `DirResult.Functions` (`dirFileCallGraph`); it finds a file's bounds
  again only when `DirResult.LangKey` differs from the language the extension gives (a `.h` under `-l c`). Files are
  scanned in parallel and reported in path order. `TestBuildDirCallGraph_ReusedBoundsMatchRefind` checks that reused
  and re-found bounds give the same graph on the fixtures. `buildFileCallGraph` looks a bare call up in the file's own
  functions and then in `knownFuncs`; it never copies `knownFuncs` (every function of the run) per file.
- Reverse lookup uses `ReverseCallers`: bare names include qualified callees with the same final name; qualified queries match exactly. Results are sorted, deduplicated name-based candidates, not type-resolved method identities. The full reverse graph preserves qualified keys.
- Language regular expressions compile on first use: `LoadConfig` only parses `languages.json`, and every accessor on `LanguageConfig` calls `ensure()` first. Read compiled fields through the accessors, never directly; `TestEveryLanguageCompiles` makes a broken pattern fail the build. `NewPythonFinder` and `NewPythonStructFinder` take the config by pointer: a copy would copy the `sync.Once`.
- `CleanLine` returns a line unchanged when `noLiteralStarts` holds: no configured string, char, doc-string, comment, or percent/regex marker occurs in it. A new marker field in `LanguageConfig` that the sanitizer reads must be added to `noLiteralStarts`; `TestCleanLineFastPathMatchesSlowPath` checks the fast path against `cleanLineSlow` on every fixture line. `char_literal_lookahead` (Rust) makes a quote in `char_delimiters` open a literal only when it closes on the same line (`charLiteralEnd`); a lifetime stays code.
- Read source files with `readFileLines` (or `ReadLines` from `cmd/`), never with `bufio.Scanner` on its default limit: a 64 KB line made the scanner stop, and a file with such a line (minified bundles) was silently truncated. `TestReadFileLines_LineLongerThan64KB` guards it. `readFileLines` reads the file whole and copies each line out once; its lines must stay `forEachLine`'s (`TestReadFileLinesMatchesForEachLine`).
- Pre-filters on cleaned lines: `func_requires` (a function header holds one of the words) and `type_keywords` (a class or struct header holds one of the words). A new function, class or struct pattern for a language must keep that word in every alternative, and the word goes into `languages.json`; `TestFuncRequiresNeverHidesAHeader` and `TestTypeKeywordsNeverHideAType` check every fixture line. The nested scan runs `declaration_pattern` only where `MayDeclare` holds (`func_requires`, and the line ends with `;`): every declaration pattern must end in `;\s*$`, which `TestMayDeclareNeverHidesADeclaration` checks. Decisions about code read the `LineFacts` of a line (`CleanLinesFacts`: the cleaned text, the start state, the indentation of the raw line, and `CodeText`), computed in one pass. The raw line is read only for the output and for quoted method names and heredoc terminators.
- Rust `nesting_pattern` (`languages.json`) matches `if`, `match`, `while` or `loop` anywhere on the cleaned line, a `for` at the start of a line, and `for … in`; `impl X for Y` is not a decision. The complexity score of Rust functions depends on it: `cmd/complexity/rust_nesting_test.go` pins the cases.
- The D and Scala lexers clean their own language (`prepareDLines`, `cleanScalaLines`) and hand their text to the finders as `lexerFacts`; the sanitizer does not run on that text again. The Scala lexer keeps each literal as a pair of parentheses, which `scalaFunctionEnd` reads, so its text is not blanked like the sanitizer's.
- Python logical lines (`pythonLogicalLines`) read the sanitizer's `LineFacts`; there is no separate Python string cleaner. Multi-line strings close at their own marker, and the rest of the line after the closing quotes is code.
- `PythonStructFinder` (`python_struct_finder.go`) reads `LineFacts` too: a class header, a decorator, a field and the end of a block count only on a code line (`pythonCodeLine`: starts outside a string and has `CodeText`). Its header and field matches read `Cleaned`, and the block end uses `Indent`. A `@dataclass` or `@attr.s` decorator sets the kind of the next class header (`dataclass`, `attrs`); a code line that is neither a decorator nor a class header clears it.
- The finders on the simple path (`findFunctionsSimple`), the class finder (`findClassesWithOffset`, whose `classHeaderContinues` reads the cleaned next line), the structural finders (`StructFinder`, `HybridStructFinder`) and the block finder (`finder_block.go`) read `LineFacts`; a line that starts outside a literal with the language's line-comment marker has no `CodeText`; the block finder steps the state with `lineFacts` and skips heredoc bodies, which are not cleaned. The raw line is read only for the heredoc terminator. A Ruby `end` is `rubyBlockEndAt` on the cleaned line.
- `processFilesParallel` hands out jobs largest file first (`Job.Size`); results come back in completion order, so every consumer of `DirResult` slices sorts them itself.
- `collectFiles` and `CollectSourceFiles` walk with `filepath.WalkDir`, which reads directory entries without a system call per entry; `collectFiles` asks `entry.Info()` for the size of source files only. Do not go back to `filepath.Walk`: on a tree with build artifacts its `Lstat` per entry was a third of a run.
- Each file is read once per job (`lazyLines` in `dirprocessor.go`): finders that take lines get the shared lines; Python's finder still reads the file itself. Tools that read a file themselves pass its lines to `FindFunctionsInFile` instead of calling `FindFunctions`, which would read it again.
- Each file is cleaned once per job too: `prepareDirJob` (`facts_cache.go`) gives the job's finders and the Go alias sanitizer one `factsCache`, and `CleanLinesFacts` returns the kept facts when the same line slice is cleaned again with the same language and raw setting. The facts are shared, so no caller may modify what `CleanLinesFacts` returns, nor the job's lines. Sharing relies on `CleanLinesFacts` not depending on what the sanitizer cleaned before (`TestCleanLinesFactsIgnoresEarlierFiles`): new sanitizer state must be set again when a literal opens, or reset at the start of `CleanLinesFacts`. `prepareDirJob` also sets the struct finders' `noFields`: a `DirResult` holds no fields. `TestDirJobSharingKeepsResults` compares directory results with and without it (`dirJobSharing`).
- `ForEachParallel` (`parallel.go`) is the per-file worker pool of the tools outside `DirProcessor` (`complexity`, `funcstats --dir`): each call writes only its own slot, and the caller reads the slots in input order, so output and error reporting match a sequential run.
- `GetLanguageByExtension` visits languages in sorted order and gives `.h` to `cpp` (both `c` and `cpp` claim it). Keep the choice stable: `--dir` output must not depend on map order.
- Go type aliases (`type A = S`, and the `A = S` lines of a `type ( ... )` group) are read by `findGoAliases` (`go_aliases.go`) from sanitized lines and kept in `DirResult.Aliases`, apart from the types. Go has no `type_alias` struct pattern (`languages.json`): an alias must not come back as a type. The other members of a `type ( ... )` group are read by the struct finder with a virtual `type ` prefix (`goGroupMemberLine`); the group open/close lines match nothing. A `named` type whose expression opens a brace (`type X []struct {`) keeps the type open until the braces balance.
- `--names` (`names.go`) prints the directory job's results: `ProcessSingleFile` runs one file through `processFile`, and `FormatNames` lists the results. Kinds come from `FunctionBounds.ClassName` (method), `ClassBounds.Kind` (empty means a class from the class finder) and `AliasBounds`. The class finder and the struct finder share one entry per declaration: the struct finder's kind is copied onto it. `functionKind` and `classKind` are the one place the kinds are named.
- `--doc` (`docs.go`) reads the raw lines above a declaration (`DocLines`): line comments, or a block comment that ends on the line above, with decorators skipped. Comments are output only, so raw lines are fine there. `DirResult.LangKey` gives the comment markers (`LineComment`, `BlockCommentStart/End`). Python docstrings are not read yet.
- `structPatternOrder` tries the Go `named` pattern last: it also matches a one-line `type X struct{}`.
- Incremental split (`ProcessDirectoryIncremental`, `WriteSplitOutputIncremental`): a shard is a file's directory, and its checksum covers all its files, sorted. A shard with no declaration has no shard file; its checksum is in `Manifest.EmptyShards` (`emptyShardChecksums`), so the next run does not take it for changed. Both split writers record it.
- Shard graph (`importresolver.go`): `BuildShardGraphFor` takes a `ResolveContext` with the language's data (Go module prefix, TS/JS aliases, Rust crates). Rust crates come from `DetectRustCrates` (`importresolver_rust.go`): each `Cargo.toml` that names a `[package]` or `[lib]`. A Rust import resolves by crate name or `crate::`, and walks the crate's `src/` shard directories as far as the tree has files. Rust imports count toward `ShardGraphStats` only when they name a known crate.
- `shardutil.go` owns all `.codemap/` path conventions; do not hardcode shard paths elsewhere.
- `IgnoreMatcher` follows git's `.gitignore` rules for the root file: `patternToRegex` reads `*`/`?` within a
  segment, `**/`, `/**` and other `**`, anchors a pattern with a leading or middle `/` to the root, and `Matches`
  compares slash-separated paths (`filepath.ToSlash`). Only a line starting with `#` is a comment.
  `TestIgnoreMatcher_GitSemantics` pins cases answered by `git check-ignore --no-index`; extend it from git, not by
  hand. Not supported: `!` negation (dropped), nested `.gitignore` files, `.git/info/exclude`, and git's index (a
  tracked file that a pattern matches is skipped, as `check-ignore` reports it).
- `Matches` checks each pattern's `literal` (`globLiteral`) with `strings.Contains` before its regex; a `**/` counts
  as a wildcard with its slash. `TestIgnoreMatcher_LiteralGateMatchesRegex` compares the gate with the bare regexes; a
  change to `patternToRegex` must keep `globLiteral` in step.

- Output formatters build their text in a `strings.Builder` (`formatDirResultsGrep`, `buildTreeOutput`/`writeTreeNode`),
  never with `+=` on a string in a loop: that copies the whole output per line, and on OmniRoute it made `--dir --map`
  take 10.9 s instead of 1.7 s.
- `DetectLanguage` (`detect.go`) gives a directory's language by source-file count, ties by language key, and a file
  by its extension. `complexity` uses it when `-l` is absent.
- `FilterExcluded` (`exclude.go`) applies `complexity`'s `-exclude` globs to a file list: a pattern matches a base name,
  or a path under the analysed root with `/`. A malformed pattern is an error.
- `FindUncalled` (`uncalled.go`) lists the functions that no code line of a tree names (`funcstats --uncalled`). A use
  is an identifier in cleaned code, so comments and strings do not count. Test files, `main`/`init` and the Go interface
  methods are not candidates. The rules are in `docs/FUNCSTATS.md`.
