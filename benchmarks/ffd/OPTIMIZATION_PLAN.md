# План оптимизации D и связанных проходов Go

Первый пилот выполнен: `ScanNeeds` передаётся до разбора; каталог JS/TS `--struct` использует существующий
поиск типов без ненужного поиска функций. [Результаты](TYPES_ONLY_PILOT.md): полный CLI быстрее в 1,21–1,81 раза,
разбор загруженных исходников — в 2,69–2,74 раза. Остальные языки и файловый контекст пока сохраняют полный проход.
Выполнен также [консервативный D-проход](D_TYPES_ONLY.md): после общей подготовки отключён поиск функций,
CLI `--struct` быстрее в 1,09–1,19 раза последовательно; при восьми потоках выигрыш небольшой и переменный.
Общая подготовка D пока сохранена. Следующий этап — C++; обнаруженные D-пробелы точности ведутся отдельно.

Дата: 2026-10-21. Исходная точка измерений — `69545b7`;
[методика и результаты](PERFORMANCE_20261021.md). План не меняет правила распознавания объявлений.

Цель: перенести в поиск типов и общий CLI решения, уже проверенные на функциях,
сохраняя независимую точность обеих программ. Начать с ненужной работы, затем уменьшать
стоимость оставшейся. Новые проценты ускорения определяются замерами, а не обещаются заранее.

## На какие готовые решения опираемся

| Проверенное решение | Где уже применяется | Как использовать дальше |
|---|---|---|
| Одно чтение и общие очищенные строки | Go `lazyLines`/`factsCache`; D `readSource`/`splitLines` | Один подготовленный вход для всех запрошенных результатов файла |
| Общий лексер, токены и пары скобок | Нативные D finders, `cpp_tokenizer.d`, `js_ts_cleaner.d` | Типы и функции используют те же токены; режим управляет работой и результатом |
| Дешёвый отбор кандидатов, отрицательные hints | D header/predicate scanners; TS recovery gate | Не вызывать тяжёлое распознавание там, где объявление заведомо невозможно |
| Быстрый ASCII-путь и отложенное декодирование | D cleaner и проверки валидности исходника | Сохранить общий автомат и Unicode fallback вместо второго лексера |
| Буферы потока, арены, `TokenPool` | `reuse.d`, native tokenizers, D cleaner | Повторно использовать временные списки, стеки и текст между файлами |
| Постепенное накопление заголовка | D multiline header joins | Не пересобирать и не декодировать один префикс на каждом шаге |
| Ограниченный общий пул задач | `ffd_run.processFiles` | Сначала убрать лишние выделения, потом менять гранулярность задач |
| Проверка оптимизированного пути эталонным | `AuditHints`, `AuditFastPaths`, token/cleaner audits | Проверять и положительные, и отрицательные решения нового быстрого пути |

Это уже реализованные механизмы, а не задачи повторной разработки. История функции D:
[TODO, оптимизации подготовки](../../TODO.md), [DLANG_PORT](../DLANG_PORT.md);

## 0. Зафиксировать базу и стоимость фаз

**Изменения:** измерительный сценарий и диагностика, без изменения поиска.

- Заморозить Go/D бинарники, исходники, флаги компиляторов и коммиты корпусов.
- Раздельно измерить чтение/обход, очистку, токенизацию и пары, поиск функций,
  поиск типов, сборку результата и вывод. При общем проходе учитывать общее время,
  не складывать его повторно в несколько фаз.
- Диагностические счётчики: число токенизаций файла, кандидатов, проверенных заголовков,
  построенных/выброшенных bounds, скопированных имён и байтов временных выделений.
- Счётчики аллокаций, audit-проверки и независимые AST работают вне измерений скорости.
  Отдельно оценивать полный CLI и разбор заранее загруженных исходников.

**Приёмка:** таблица горячих фаз для `functions`, `all`, `struct` при 1/8 потоках;
сохранённые входы/результаты и все образцы времени. Старую сборку сохранять до окончания серии.

## 1. Передавать потребности режима до запуска finder

**Файлы:** `ffd_main.d`, `ffd_run.d`, `ffd_langs.d`, `ffd_file.d`, нейтральные модели.

Сейчас `applyMode` удаляет уже построенные функции. Ввести внутренний набор потребностей
разбора, передаваемый в существующие finders: выдача функций/типов, необходимость диапазонов
функций и владения, сигнатур, полей и комментариев. Выдача функции и необходимость её границ —
разные требования. Сначала добавить этот путь с полностью прежним поведением.

| Потребитель | Что действительно необходимо |
|---|---|
| Каталог `--struct --json` | Типы, псевдонимы и нужный для них контекст; без выдачи функций/полей/сигнатур |
| Каталог `--all --json` | Функции и типы из одного подготовленного входа; без полей и извлечения текста |
| Файл `--struct` с полями | Типы и контекст/диапазоны, необходимые для исключения методов и локальных полей |
| Извлечение типа | Границы типа и оригинальный текст; без вычисления полей |
| `--names`, `--doc`, `--tree-full` | Состав деклараций и метаданные, реально нужные конкретному режиму |

Нельзя просто пропускать тела функций: внутри встречаются локальные типы, а у Java/PHP —
анонимные/локальные классы. Нельзя без проверки выкинуть поиск Go aliases: он также участвует
в отделении псевдонимов от обычных типов. Различные normal/raw представления нельзя смешивать
в одном кэше. `--all --raw` сохраняет отдельные правила для функций и типов.

**Приёмка:** все прежние CLI-результаты и диапазоны сохранены; новые счётчики пока подтверждают
прежний объём работы. Публичные ключи не меняются.

## 2. Первый пилот типов — JS/TS

**Готовые компоненты:** `js_ts_cleaner.d`, `ffd_hybrid.hybridTypes`;
**изменения:** маршрутизация в `ffd_langs.d`, передача потребностей.

- Для каталога `--struct` использовать существующий cleaner и `hybridTypes`, не запускать
  `findJavaScript`/`findTypeScript` и function recovery.
- Сохранить нынешний набор struct-mode типов и их kind; `--all` по-прежнему объединяет
  нативные классы и hybrid types по существующим правилам.
- Файловые поля подключать отдельным шагом: сначала сохранить прежний полный контекст там,
  где он требуется; не менять принадлежность полей ради ускорения.

**Приёмка:** на Express/zod и целевых примерах нет изменений types/aliases/kinds/start/end;
audit подтверждает отсутствие пропущенных кандидатов. Счётчики показывают ноль построенных
function bounds и отсутствие function recovery в режиме каталога `--struct`.

Это первый небольшой коммит с измеримым эффектом; не переписывать сразу все 15 языков.

## 3. Перенести ограничение работы в остальные нативные finders

**Порядок:** D и C++ → Go/C#/Java → остальные языки по результатам профиля.
Ориентиры первых двух: заметный проигрыш `--struct` на arsd и fmt.

- Использовать существующие лексеры, пары скобок, type-header scanners и обход областей.
  Не заводить отдельную regex-грамматику типов.
- Отключать поиск и материализацию функций, когда они не нужны потребителю.
  Не отключать необходимое распознавание контекста: лексическая граница области может
  требоваться и при отсутствии function bounds в результате.
- В D проверить, какие этапы hints/контрактов/склейки заголовков нужны только функциям.
  Убирать их в types-only лишь после проверки вложенных типов и исходных координат.
- Перенести gates по ключевым словам/типу токена и отрицательные hints. Gate должен быть
  консервативным: сомнение оставляет обычный путь, а не отбрасывает объявление.
- Не копировать результаты функций, которые затем удаляются; не декодировать и не
  нормализовать повторно уже подготовленный текст.

**Приёмка каждого языка:** независимый AST/grammar/compiler профиль не ухудшился;
сохранены виды, вложенность, псевдонимы, начала/концы и порядок результатов. Оптимизации и
исправления ранее найденной ошибки оформляются отдельно, чтобы объяснять каждую дельту.

## 4. Один набор токенов для C++-проходов Go

**Файлы:** `internal/cpp_members.go`, `finder.go`, общий контракт `braceTokens`.

Это отдельная ветка плана: оптимизировать обе программы, а не оставлять дорогой Go-эталон.

- Поделиться подготовленными токенами и парами между поиском вложенных классов,
  `cppExpressionHeaders` и `recoverCppMembers`.
- Временные результаты держать в структуре одного файла; исключить повторные преобразования
  строк в runes, пересборку пар и дублирование списков. Сначала общий immutable view,
  затем уменьшение карт и временных выделений по профилю.
- Согласовать обработку директив и продолженных строк. Различные старые правила нельзя
  молча заменить общими: изменение состава объявлений требует отдельной проверки точности.
- Дешёвые gates использовать перед дополнительной проверкой выражений, когда отсутствие
  риска доказано. Не отключать фильтрацию вызовов, default arguments и конструкторов.

**Приёмка:** прежние исправления C/C++ сохраняются, реальные объявления не теряются;
число общих токенизаций снижается. Цель — убрать измеренную добавочную стоимость на fmt
относительно предыдущей локальной сборки; конкретный выигрыш подтвердить новой серией.
Go и D затем повторно сравниваются с обеими замороженными Go-базами.

## 5. Память, копирование и масштабирование D

После удаления ненужных проходов измерить оставшиеся аллокации, а не переносить старый
профиль автоматически на новую программу.

- Расширять существующие `TokenPool`/арены на горячие стеки областей, кандидаты,
  промежуточные bounds и списки результатов. Не строить ещё один механизм пулов.
- Использовать буферы на поток и `reserve`/запись по индексу там, где профиль показывает
  дорогие `~=`. Не заменять все append механически.
- Копировать имена только при включении объявления в долгоживущий результат. Результат
  не должен ссылаться на очищаемую арену следующего файла; контракт `.idup` сохраняется.
- Поля, doc-комментарии и полные сигнатуры вычислять только по запросу потребителя.
- Сохранить ASCII-путь и Unicode fallback с общей машиной состояний и сравнительным audit.

Затем проверить 1/2/4/8/16 потоков и гранулярность очереди для множества мелких файлов.
Переиспользовать существующий пул и сортировку крупных файлов первыми; увеличение числа
потоков само по себе не устраняет конкуренцию аллокатора. Порог пакетирования задач брать
из замеров. Изменять default 8/max 16 только после отдельного подтверждения на целевых машинах.

## Общая проверка после каждого этапа

1. Точность: ложные записи, пропуски, имена, виды, владение, начала и концы отдельно;
   независимый эталон языка и минимальные регрессии. Совпадение Go/D само по себе недостаточно.
2. Совместимость: сохранённые результаты собственной базовой версии, текущие 2 504 CLI-проверки,
   поля/извлечение/диапазоны/raw/names/doc/tree, split/inc и 1/8-worker детерминизм.
3. Скорость: сначала in-process parser на загруженных входах, затем полный CLI;
   прогрев, минимум 7 перемешанных раундов, все образцы/выбросы и хеши сохранены.
4. Не измерять с allocation/audit диагностикой. Незаметный на фоне разброса результат
   считать неопределённым. Повторяемое замедление нетронутых режимов более 3% — повод
   переснять замер и расследовать; это локальный бюджет, не порог для шумного CI.
5. Принимать изменение за устойчивый измеренный выигрыш без ухудшения точности.
   Не обещать фиксированное ускорение от каждого этапа. Клоны создавать временно,
   сохранять коммиты/хеши/отчёты и затем удалять только созданные тестовые каталоги.

## Порядок небольших изменений

1. База/счётчики → внутренние потребности с прежним поведением.
2. JS/TS directory types-only пилот и замер.
3. D/C++ types-only, затем остальные языки по профилю.
4. Общие C++-токены Go и отдельный замер стоимости проверок точности.
5. Остаточные аллокации D, затем гранулярность задач и повтор всей матрицы.

Первый целевой результат — убрать нынешний проигрыш D в `--struct`, сохранив выигрыш
`functions`/`all`. Разбор `schedule`, macro/impl и других ошибок остаётся обязательной
работой точности, но не смешивается с изменениями скорости в одном эксперименте.
